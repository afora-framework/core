# Building with an agent

An agent can write an afora application the way a person does, in TypeScript. It can also write it as data: an [`afora.json`](afora-json.md) that [`@afora/mcp`](../packages/mcp/README.md) validates and turns into TypeScript with `@afora/codegen`. This guide sets that up, and shows what you review and what CI checks. The point is that the rules the agent declares (a unique email, a masked password, who may call what) are enforced by the runtime, so a review reads declarations instead of searching handlers for what was forgotten.

## 1. Install

```bash
bun add @afora/core typebox
bun add -d @afora/codegen @afora/mcp
# or: npm install @afora/core typebox && npm install -D @afora/codegen @afora/mcp
```

The server speaks MCP on standard input and output, so the agent's client starts it. With Claude Code:

```bash
claude mcp add afora -- bunx @afora/mcp --project .
```

Any MCP client that starts a stdio server takes the same command:

```json
{
	"mcpServers": {
		"afora": { "command": "bunx", "args": ["@afora/mcp", "--project", "."] }
	}
}
```

The server runs on Node (`npx @afora/mcp`) as well. Importing your TypeScript needs Bun on the `PATH`: `afora_extract` does it, and `afora_project` when it is given an application (`--app` or `app`). `afora_generate` type-checks with the TypeScript installed in the project (`node_modules/typescript`), run by the server's runtime; without it the result says so and nothing is type-checked. The flags are in the [command line reference](cli.md#afora-mcp).

## 2. Ask for a change

Ask in domain terms: "a blog with users who sign up with an email and a password, posts with a unique slug, only the author may publish a post, served over HTTP with an OpenAPI document". The server's guide (the resource `afora://spec/guide`) tells the agent the workflow, and the tools keep it on that path:

| Step | Tool                                     | What the agent gets                                                                                                       |
| ---- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 1    | `afora_catalog`                          | What a spec can use: the std properties and record plugins, reserved keys, repository rules, the providers and stages.    |
| 2    | `afora_spec_read`, `afora_project`       | The spec as it is, with its issues, and the project as a map: entities, operations, their routes and who may call them.   |
| 3    | `afora_spec_upsert`, `afora_spec_remove` | One declaration at a time. The whole spec is validated on each write, and an invalid one is not written.                  |
| 4    | `afora_spec_validate`                    | Every issue, each with a path and a stable `code`.                                                                        |
| 5    | `afora_generate`                         | The TypeScript, written into `output.dir`, and the type errors of the generated files, which the agent fixes in the spec. |

The server never writes an invalid `afora.json`, so the agent cannot leave it half broken between two calls. A rule that does not fit a declaration goes in a function the spec imports (`{ "import": "./rules.ts#canPublish" }`): see [When steps are not enough](afora-json.md#when-steps-are-not-enough).

## 3. Review it

What changed is two things, both in the diff:

- **`afora.json`**: the declarations. This is where a review spends its time: an entity's `unique` and `sensitive` keys, a repository's `actions`, a use case's `access` and `route`, an output's `statuses`.
- **The generated code** under `output.dir` (`src/domain` by default). Each file starts with `// Generated by @afora/codegen from afora.json. Do not edit.`, and `generate` only overwrites or removes files that carry that line. A file of yours is never replaced.

Behavior you add by hand lives in files of your own: extend a generated class, or point the spec at a function or class with `import`. Both survive the next `generate`.

## 4. Keep it honest in CI

Three checks keep the spec, the code and the database in step. With Bun (`npx` in place of `bunx` on Node; `schema check` imports TypeScript, so Node >= 22.18, where type stripping is on by default):

```bash
bunx afora-codegen check                                       # the spec is valid
bunx afora-codegen generate && test -z "$(git status --porcelain)"  # the committed code is what the spec gives
bunx afora-codegen schema check src/domain/application.ts#App  # a change to an entity declares what its stored rows need
```

The second line fails when someone edited a generated file or the spec without generating again, including when `generate` writes a file that was never committed. The third compares the entities with the committed `afora.lock.json` ([Schema evolution](schema-evolution.md#from-commit-to-production)).

## 5. Providers and servers the spec can name

A spec names its provider and its stages by name: `inMemory`, `select` and `openapi` are built in. Others come from catalogs, which the companion packages export. Give the server a module of the project that gathers them:

```ts
// afora.catalog.ts
export { providers } from "@afora/drizzle";
import { stages as hono } from "@afora/hono";
import { stages as ws } from "@afora/ws";
export const stages = [...hono, ...ws];
```

```bash
claude mcp add afora -- bunx @afora/mcp --project . --providers afora.catalog.ts --stages afora.catalog.ts
```

Pass the same flags to `afora-codegen check` and `generate` in CI. `afora_catalog` then lists `drizzle`, `hono` and `websocket`, and the agent can write `"provider": { "use": "drizzle", ... }` or a `{ "sink": "hono" }` stage.

## 6. A project written in code

Without an `afora.json`, start the server with `--app src/app.ts#App`. `afora_project` then reads the application directly, hand-written use cases, `@Route` and `@Access` included, and the guide tells the agent to add to such a project in TypeScript, in the style it finds there. The declarations hold the same guarantees in both forms. When a project has both, `afora_project` lists where they differ.

## 7. What the server will not do

The input of the server comes from an agent and is treated as untrusted. Every write stays inside `--project`; an `import` or `extends` that leaves the project, or names a module built into the runtime, is refused with `outside_project`; nothing an agent sends is executed, it can only name files of the project to import. The full trust model is in the [package README](../packages/mcp/README.md#safety).

## The other direction

`@afora/mcp` also turns an application into MCP tools: the `mcpTools` sink serves the operations of an output to an agent, with the same validation, access checks and masked responses as HTTP. See [Expose an output as MCP tools](../packages/mcp/README.md#expose-an-output-as-mcp-tools).
