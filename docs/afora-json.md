# afora.json

An `afora.json` describes a domain as data: properties, blueprints, records, entities, environments, repositories, exceptions, use cases (with their steps), commands and outputs. `@afora/codegen` turns it into the TypeScript you would have written by hand, and turns an `Application` back into an `afora.json`. The code is committed and reviewable; nothing is interpreted at runtime.

This guide is the workflow. The reference of every declaration, option and issue code is in [packages/codegen](../packages/codegen/README.md), the same spec is authored by an agent through [packages/mcp](../packages/mcp/README.md), and `afora.schema.json` (in `@afora/codegen`) is its JSON Schema, for editors (`"$schema": "./node_modules/@afora/codegen/afora.schema.json"`).

## The workflow

```bash
bun add @afora/core typebox
bun add -d @afora/codegen
# or: npm install @afora/core typebox && npm install -D @afora/codegen
```

```bash
afora-codegen check [afora.json] [--providers module] [--stages module]                 # validate
afora-codegen generate [afora.json] [--out dir] [--providers module] [--stages module]  # write the code into output.dir
afora-codegen extract src/app.ts#App [--import key=./file.ts#name] > afora.json
```

1. Write the spec. The quick start in the [README](../README.md#the-same-app-as-an-aforajson) is a complete one.
2. `check` validates it. Every issue has a path, a stable `code` and a message, and `generate` throws `InvalidSpecError` with the same issues instead of writing a partial result.
3. `generate` writes one file per kind of declaration into `output.dir` (`src/domain` by default), an `application.ts` with `export const App = applicationOf({...})` and an `index.ts`. The output is deterministic, formatted as Biome would, and every file starts with `// Generated by @afora/codegen from afora.json. Do not edit.` It only overwrites or removes files that carry that banner, and writes nothing if one would be refused.
4. Add behavior in files of your own: extend a generated class, or point the spec at a hand-written function or class with `{ "import": "./file.ts#name" }`. Imports are relative to the output directory.
5. Commit the generated code. A test that generates again and compares it with the committed files catches drift; `examples/blog` does exactly that.

`extract` imports the file, so use Bun (or Node >= 22.18, type stripping on by default) for TypeScript files. The CLI runs on Node >= 22 or Bun. The same functions are available from code: `loadSpec`, `validateSpec`, `generate`, `writeGenerated`, `extractSpec`, `normalizeSpec`, `catalog`.

## Versioned entities and increment

An entity takes `"versioned": true`, generated as `entityOf(..., { versioned: true })` and extracted back from `describe()`: it gets a `version` identity key, so its fields cannot declare `version` (`identity_key`) nor its `change` name it (`change_identity`), and `update` throws `RepositoryConcurrencyConflict` (409) on a stale write (see [Repositories](repositories.md)). A record does not take it (`unknown_key`).

A repository lists `"increment"` among its actions for atomic counters; the entity needs a number key (a Std `integer` or `number` property, not a list) in its `change` (`increment_needs_number` otherwise). It is called by code written by hand: a `find` step cannot call it (`write_in_find`), and there is no step for it.

```json
{
	"entities": {
		"PageViews": {
			"fields": { "entry": "text", "views": "integer" },
			"change": ["views"],
			"versioned": true
		}
	},
	"repositories": {
		"Views": {
			"entity": "PageViews",
			"actions": ["findById", "update", "increment"]
		}
	}
}
```

## Ids

An entity takes `"id"`, how its ids are made: `"uuid7"` (the default, as when it is left out), `"uuid"` (any UUID version, a v4 from an existing database included; new ones are still v7), `"key"` (a natural key of 1 to 256 characters that the input of `create` must hold, never generated) or `"serial"` (a positive integer the database assigns on `create`, from an auto-increment, serial or identity column; the provider must assign ids, as the in-memory and Drizzle ones do, see [Entities](entities.md#ids-the-database-assigns)). They are generated as `entityOf(..., { id: Uuid })`, `{ id: Key }` and `{ id: Serial }` and extracted back from `describe()`; an entity whose id is a custom `idOf` cannot be extracted (`ExtractionError`). A record does not take it (`unknown_key`), and any other value is `invalid_option`.

The spec therefore says the type of an id on the wire: a string for `"uuid7"`, `"uuid"` and `"key"`, and an integer (a JSON number) for `"serial"`. A client built from the spec types the `id` of an entity from it, as `string` or `number`, and need not accept any JSON. `catalog().idStrategies` lists the values with their `wire` type, and `idWireTypeOf(entity)` reads it from a declaration (`"string"` when `id` is left out). `toOpenAPI` and `jsonSchemaOf` give the generated entity the same type (`type: "string"` or `type: "integer"`), which the tests of `@afora/codegen` compare.

```json
{
	"entities": {
		"Setting": { "fields": { "value": "text" }, "id": "key" },
		"Customer": { "fields": { "name": "text" }, "id": "uuid" },
		"Ticket": { "fields": { "title": "text" }, "id": "serial" }
	}
}
```

## Schema evolution

An entity takes `schemaVersion`, `previousNames` and `upgrade` (each step an import of a hand-written function, by the version it reaches), and the object form of a type or enum field takes `fill` and `renamedFrom` (see [Schema evolution](schema-evolution.md)):

```json
{
	"entities": {
		"Entry": {
			"fields": {
				"title": { "type": "text", "renamedFrom": "name" },
				"locale": { "enum": ["pt", "en"], "fill": "pt" }
			},
			"schemaVersion": 2,
			"previousNames": ["Post"],
			"upgrade": { "2": { "import": "./upgrades#entryV2" } }
		}
	}
}
```

They are generated as `.with({ fill, renamedFrom })` and the options of `entityOf`, and extracted back (`entities.<Name>.upgrade.<n>` in `imports` for a step). `afora-codegen schema lock src/app.ts#App [--out afora.lock.json]` writes the [schema lock](schema-evolution.md#the-lock), and `afora-codegen schema check src/app.ts#App [--lock afora.lock.json]` fails in CI when the lock is stale, a change lacks its declaration or a version was not bumped, printing an `upgrade` stub for each missing step.

## Variant fields

A field that holds one of several objects, told apart by the value of one key ([`variantOf`](blueprints.md#one-of-several-blueprints)), is `{ "variant": { "key", "of" } }`, next to the `type`, `enum` and `fields` forms. `of` maps the value of the key to each variant: the name of a declared blueprint, record or entity, or a blueprint declared in place (`{ "fields": {...} }`). `optional` and `list` apply as to the other forms; `with`, `fill` and `renamedFrom` do not.

```json
{
	"entities": {
		"Payment": {
			"fields": {
				"method": {
					"variant": { "key": "method", "of": { "card": "Card", "pix": "Pix" } }
				},
				"events": {
					"variant": {
						"key": "type",
						"of": {
							"click": "Click",
							"visit": { "fields": { "path": "string" } }
						}
					},
					"list": { "maxItems": 10 },
					"optional": true
				}
			}
		}
	}
}
```

It is generated as `ctx.variantOf("method", { card: Card, pix: Pix })`, wrapped in `listOf` and `optionalOf`, and extracted back from `describe()`. The validator checks that `key` is a string that is not empty and that `of` has at least one variant (`invalid_variant`), that each name is declared (`unknown_type`) and is a blueprint, a record or an entity (`wrong_kind`), that no variant declares the key, which the field adds (`invalid_variant`, an entity's identity keys and a plugin's keys included), and that a record or an entity is not two variants (`invalid_variant`: an instance is told apart by its class). An entity among the variants needs its repository in the `relations` of the holder's repository, as for any entity field (`missing_relation`). A variant field cannot be an environment variable (`invalid_environment_field`) nor the `orderBy` of an index (`invalid_index`), and `$input.<field>.<key>` in a step is checked against the key and the keys of every variant.

## Files

A field that holds a file ([`fileOf`](std-properties.md#files)) is `"file"` for any file, or `{ "file": { "types": ["image/png", "image/*"], "maxBytes": 5000000 } }`, next to the `type`, `enum`, `fields` and `variant` forms; `{ "file": {} }` is any file too, and `name` names the property. `optional` and `list` apply; `with`, `fill` and `renamedFrom` do not. A property declaration takes the same form, `{ "file": {...}, "optional"?: true }`. It is generated as `ctx.fileOf({ types, maxBytes })` (`fileOf` for a declaration) and extracted back from `describe()`. The validator checks that `types` is a non-empty list of media types, that `maxBytes` is a whole number, 0 or more, and that nothing else is given (`invalid_file`, `unknown_key`); a file cannot be an environment variable (`invalid_environment_field`), a field of an entity, at any depth of fields in place (`entity_file`: store its URL instead), nor `sensitive` or `unique` (`invalid_file`). An HTTP output reads the input of a use case that holds one from a `multipart/form-data` body: see [Outputs](outputs.md).

```json
{
	"useCases": {
		"UploadMedia": {
			"input": {
				"fields": {
					"file": {
						"file": {
							"types": ["image/png", "image/jpeg"],
							"maxBytes": 5000000
						}
					},
					"folder": "string?"
				}
			}
		}
	}
}
```

## Money

A field that holds an amount of money ([`ctx.money`](std-properties.md#money)) is `{ "money": { "currency": "BRL" } }` for an amount in one currency, whose value is the integer of minor units alone, or `{ "money": { "currency": ["BRL", "USD"] } }` and `{ "money": {} }` (any ISO 4217 code) for one that carries its currency, `{ "amount": 1999, "currency": "BRL" }`. `min` and `max` (integers of minor units), `nonNegative` and `name` are the other options. `optional` and `list` apply; `with`, `fill` and `renamedFrom` do not. A property declaration takes the same form, `{ "money": {...}, "optional"?: true }`. It is generated as `ctx.money({ currency, min, max, nonNegative })` (`moneyOf` for a declaration) and extracted back from `describe()`. The validator checks the options as `moneyOf` does: a currency of three upper-case letters, or a non-empty list of different ones, bounds that are safe integers, a `min` (or 0, with `nonNegative`) no greater than `max`, and nothing else (`invalid_money`, `unknown_key`). An amount that carries its currency is an object: it cannot be an environment variable (`invalid_environment_field`) nor a key of an index, and `$input.<field>.amount` and `$input.<field>.currency` are its keys in a step; one in a single currency is an integer and can be both.

```json
{
	"blueprints": {
		"Checkout": {
			"fields": {
				"subtotal": { "money": { "currency": "BRL", "nonNegative": true } },
				"total": { "money": { "currency": ["BRL", "USD"] } }
			}
		}
	}
}
```

## A list as the response

The `response` of a use case written in the spec is a blueprint (its name, or `{ "fields": {...} }`), or a list written as a list field, for a use case that [answers an array](use-cases.md#a-list-as-the-response):

```json
{
	"useCases": {
		"RecentArticles": {
			"input": { "fields": { "limit": "integer" } },
			"response": { "type": "ArticleSummary", "list": { "maxItems": 50 } },
			"implementation": {
				"import": "../handlers/recent-articles.ts#RecentArticles"
			}
		}
	}
}
```

`"ArticleSummary[]"` is the same list without bounds, `"string[]"` a list of a property, and `{ "fields": {...}, "list": true }` a list of objects declared in place. It is generated as `listOf(ArticleSummary, { maxItems: 50 })` and extracted back from `describe()`, whose use case has `responseList` (and `response: {}`) for it. The response must be a list, not optional, and not of variants (`invalid_blueprint`); a type it names must be declared (`unknown_type`). A list has no keys, so a `route.setCookie` with it is `invalid_route`.

## Round trip

`extractSpec(app)` reads `app.describe()` and is the inverse of `generate`: `spec -> generate -> import -> extractSpec` gives back the same spec, and `normalizeSpec` makes the shorthand and object forms of a field compare equal. This holds for code that was generated, and for code written by hand, as long as everything the core cannot describe is mapped to an export (next section). An unmapped piece makes extraction throw an `ExtractionError` naming the key, instead of guessing. `examples/blog` extracts its own spec back in its tests, and `bun run test:roundtrip` proves both directions on complete applications.

## Mapping what cannot be described

Some things are code, not data: a provider made by hand, a `run` function, the `before` and `after` of a standard use case, an `execute`, the methods of an entity, a command's event handler, a stage. Extraction needs to know where each one is exported from. In the CLI it is `--import key=./file.ts#name`, in code `extractSpec(app, { imports: { key: "./file.ts#name" } })`.

| Key                                | Maps                                                                          |
| ---------------------------------- | ----------------------------------------------------------------------------- |
| `provider`                         | the provider of the application, when created without `providerOf`            |
| `log`                              | the `log` of the application, when made by `logFrom`                          |
| `log.providers.<index>`            | a log provider other than `"console"` or `"json"`, by its position            |
| `trace`                            | the tracer of the application (`trace`), always written by hand               |
| `repositories.<Name>.provider`     | the own provider of a repository, when created without `providerOf`           |
| `providers.<key>`                  | a provider of the top-level `providers`, when created without `providerOf`    |
| `useCases.<Name>`                  | a use case with a hand-written `execute`                                      |
| `useCases.<Name>.run.<name>`       | the `fn` of a `run` step of a steps use case                                  |
| `useCases.<Name>.before`, `.after` | the `before` and `after` of a standard use case                               |
| `commands.<Name>.events`           | the event handler of a command, when it is not a policy                       |
| `commands.<Name>.onEventError`     | the `onEventError` handler of a command                                       |
| `publishers.<key>`                 | a publisher of the top-level `publishers`                                     |
| `services.<name>`                  | the factory of a service of the top-level `services`                          |
| `entities.<Name>`                  | an entity whose class declares methods of its own                             |
| `entities.<Name>.events.<event>`   | the handler of an event of an entity (a cycle or `emits`)                     |
| `outputs.<Name>.pipe.<index>`      | a stage written by hand, or a sink given hooks, by its position in the `pipe` |
| `<property name>`                  | the module of a property that cannot be recreated (see the limitations)       |

The value is always `"./file.ts#export"`.

## Event policies and publishers

A command's `events` can name an event policy of the catalog with JSON options, generated as the call of its factory and extracted back as written. `publishEvents` is built in (see [Commands](commands.md#event-policies)); its `publisher` is a key of the top-level `publishers`, each a publisher written by hand:

```json
{
	"publishers": { "realtime": { "import": "../realtime.ts#hub" } },
	"commands": {
		"Posts": {
			"useCases": { "create": "CreatePost" },
			"events": {
				"policy": "publishEvents",
				"options": { "publisher": "realtime", "topic": "posts/{id}" }
			}
		}
	}
}
```

`realtime.ts` exports the publisher, any object with a `publish(topic, event)` method, such as `export const hub = wsHub();` of [`@afora/ws`](../packages/ws/README.md), whose `{ "sink": "websocket" }` serves the operations and the subscriptions (`--stages ./stages.ts`, a local module with `export { stages } from "@afora/ws";`). The generated application gets `publishers: { realtime: hub }`, and a spec that extends this one can name `realtime` too. The validator makes a built-in policy with its options, so what it would throw is an `invalid_event_policy_options` issue; a name outside the catalog is `unknown_event_policy`, a `publisher` that is not a key of `publishers` (own or inherited) `unknown_publisher`, and a publisher that is not an import `invalid_import`. Extraction needs `publishers.<key>` in `imports`.

## Services

A use case that needs what is not a repository (a cache, a storage, a client of another API) names a service in its `dependencies`, a key of the top-level `services`, whose value is the factory written by hand that makes it once per call (see [Services](use-cases.md#services)):

```json
{
	"services": { "cache": { "import": "../services.ts#cache" } },
	"useCases": {
		"GetContent": {
			"input": { "fields": { "key": "string" } },
			"response": { "fields": { "value": "string" } },
			"dependencies": { "cache": "cache" },
			"implementation": { "import": "../handlers/get-content.ts#GetContent" }
		}
	}
}
```

`services.ts` exports the factory, `(scope: ServiceScope) => value`, maybe async. The use case is generated with `cache: serviceOf<Awaited<ReturnType<typeof cache>>>("cache")`, so its hand-written `execute` reads `this.dependencies.cache` typed by what the factory returns (imported with `import type`, so loading the use case never loads `services.ts`), and the application with `services: { cache }`. A spec that extends this one can name `cache` too, typed the same when this spec is extended by a relative path or the factory is imported from a package; a factory relative to a spec reached as a package, or one of a spec that an extended spec extends in turn, is not importable from the child, and the service is `unknown` there. Steps do not read a service. A name of `services` must be an identifier other than `Logger` (`invalid_name`) and cannot be the name of a declaration (`duplicate_name`); a dependency that names neither a declaration nor a service is `unknown_dependency`. Extraction needs `services.<name>` in `imports`.

The events come from the lifecycle of the entities and from their methods. An entity (not a record) declares those of each cycle by `onCreate`, `onUpdate` and `onDelete`, and those its methods raise with `this.emit` in `emits`, each one event or a list:

```json afora:entities
"Post": {
	"fields": { "title": "text" },
	"events": {
		"onCreate": "created",
		"onUpdate": ["changed", { "name": "audited", "handler": { "import": "../audit.ts#onAudited" } }],
		"emits": ["published"]
	}
}
```

A name alone is an event without a handler, raised to be published; `{ name, handler }` runs a handler written by hand first (with `publishEvents`, unless `handle: false`). They are generated as `export const PostEvents = { created: eventOf("created", Post), ... }`, and the entity gets `onCreate: () => PostEvents.created`; so no declaration may be called `PostEvents` (`name_collision`). The entity gets `emits: () => [PostEvents.published]`, and `describe()` lists them. One name is one event: naming it in two keys (a cycle and `emits`, say) with different handlers is `event_conflict`. The methods that raise the events in `emits` need a class written by hand (see [Entities with methods](#entities-with-methods)), which raises them as `this.emit(BookingEvents.confirmed)`; `emit` still accepts an event that is not declared. Extraction gives them back from `describe()`, and needs `entities.<Name>.events.<event>` in `imports` for each handler.

## Tracing

`"trace"` is the tracer of the application (see [Tracing](tracing.md)), an import of one written by hand, such as `otelTracer()` of [`@afora/otel`](../packages/otel/README.md):

```json afora
{
	"version": 1,
	"name": "blog",
	"trace": { "import": "../trace.ts#tracer" }
}
```

`trace.ts` has `export const tracer = otelTracer();` and the generated application gets `trace: tracer`. Anything but an import is `invalid_trace`, a malformed one `invalid_import`. `describe()` gives the trace as `{ kind: "opaque" }`, so extraction needs `trace` in `imports`.

## Indexes and query cost

A repository declares its [indexes](repositories.md#indexes) and what it does with a [scan](repositories.md#query-cost) as in TypeScript:

```json afora:partial
"repositories": {
	"Entries": {
		"entity": "Entry",
		"actions": ["create", "findMany", "findCursor", "explain"],
		"indexes": {
			"byTypeStatus": { "where": ["type", "status"], "orderBy": "publishedAt" },
			"byOwner": { "where": ["ownerSub"] }
		},
		"scans": "reject"
	}
}
```

They are generated as `indexes` and `scans` of `repositoryOf`, given by `describe()` and extracted back; normalization leaves out no indexes and `"scans": "allow"`, the default. A key that is not a key of the entity is an `unknown_index_key` issue; a sensitive `orderBy` (a sensitive key may be in `where`), an `orderBy` that is not scalar, a key listed twice, an empty or malformed index and two indexes on the same keys and order are `invalid_index`.

## Parents

A repository names the [parents](repositories.md#parents) of its entities as in TypeScript, by the key holding the id of the parent:

```json afora:partial
"repositories": {
	"Courses": { "entity": "Course", "actions": ["create", "findById", "delete"] },
	"Modules": {
		"entity": "Module",
		"actions": ["create"],
		"deletion": "soft",
		"parents": { "courseId": { "repository": "Courses", "onDelete": "cascade" } }
	},
	"Lessons": {
		"entity": "Lesson",
		"actions": ["create"],
		"parents": { "moduleId": { "repository": "Modules", "onDelete": "restrict" } }
	}
}
```

They are generated as `parents` of `repositoryOf` (the parent repository is declared first), given by `describe()` and extracted back; normalization orders them by key and leaves out an empty `parents`. A malformed parent, a key that is not a key of the entity, an identity key or a key that does not hold a single value is `invalid_parents`; a repository that is not declared is `unknown_repository`; a parent whose repository, or one above it, stores the entity of the child is `parent_cycle`.

## Records that expire

An entity (not a record) declares when its records expire with `expires`, generated as the [option of `entityOf`](entities.md#records-that-expire) and extracted back from `describe()`:

```json afora:entities
"AuditEvent": { "fields": { "action": "text" }, "expires": { "after": { "days": 400 } } },
"Window": { "fields": { "hits": "integer", "until": "dateTime?" }, "expires": { "at": "until" } }
```

`after` is a non-empty duration (`days`, `hours`, `minutes`, `seconds`, each a positive number) from `createdAt`, kept in an `expiresAt` identity key, so no field may be named `expiresAt` (`identity_key`). `at` names a `dateTime` or `date` field of the entity (optional or not); a record without a value never expires. Anything else is an `invalid_expires` issue. Repositories of the entity leave expired records out of every read unless `withExpired: true` (see [Repositories](repositories.md#records-that-expire)), and need a provider with `capabilities.expiry` (`"inMemory"` and `drizzle` have it).

## When steps are not enough

Steps are a sequence with no branching, no loops and no expressions (see [what steps will never have](use-cases.md#what-steps-will-never-have)). When a rule needs one, the use case moves to `import`: the same declaration, with a hand-written `execute` in place of its steps. Its input, response, context, dependencies, errors, route and access stay in the spec, so the operation, its validation and the use cases that call it do not change.

`Reserve` takes stock away from an item, and fits in steps:

```json afora:useCases
"Reserve": {
	"input": { "fields": { "itemId": "id", "quantity": "integer" } },
	"response": { "fields": { "status": { "enum": ["reserved", "back-ordered"] }, "item": "Item" } },
	"dependencies": { "items": "Items" },
	"errors": ["ItemNotFound"],
	"implementation": {
		"steps": [
			{ "find": "items.findById", "args": ["$input.itemId"], "as": "item" },
			{ "ensure": "exists", "value": "$item", "error": "ItemNotFound" },
			{ "run": "remaining", "fn": { "import": "../stock#remaining" }, "args": ["$item.stock", "$input.quantity"], "params": { "fields": { "stock": "integer", "quantity": "integer" } }, "as": "stock" },
			{ "change": "$item", "key": "stock", "value": "$stock", "as": "changed" },
			{ "update": "items", "value": "$changed", "as": "saved" },
			{ "return": { "status": "reserved", "item": "$saved" } }
		]
	}
}
```

Then the rule changes: when the stock is short, leave it as it is and answer `back-ordered`. That is a branch, so `Reserve` moves to code. Only `implementation` changes:

```json afora:useCases
"Reserve": {
	"input": { "fields": { "itemId": "id", "quantity": "integer" } },
	"response": { "fields": { "status": { "enum": ["reserved", "back-ordered"] }, "item": "Item" } },
	"dependencies": { "items": "Items" },
	"errors": ["ItemNotFound"],
	"implementation": { "import": "../handlers/reserve#Reserve" }
}
```

`generate` now writes `export abstract class ReserveBase extends useCaseOf({...}) {}` in `src/domain/reserve.use-case.ts` (the file is named after the use case in kebab case), with the declaration above. The class is written once, at the path the spec names (relative to the output directory), and `application.ts` registers it:

```ts
// src/handlers/reserve.ts
import { ItemNotFound } from "../domain/exceptions";
import { ReserveBase } from "../domain/reserve.use-case";

export class Reserve extends ReserveBase {
	override async execute() {
		const item = await this.dependencies.items.findById(this.input.itemId);
		if (!item) throw new ItemNotFound({ source: "Reserve" });
		if (item.stock < this.input.quantity) {
			return { status: "back-ordered" as const, item };
		}
		item.change.stock(item.stock - this.input.quantity);
		const saved = await this.dependencies.items.update(item);
		return { status: "reserved" as const, item: saved };
	}
}
```

## Entities with methods

State transitions belong in the entity, as methods that change it and raise events (see [Entities](entities.md)). A method is code, so an entity that has some names its class with `implementation`, the same way a use case names its `execute`; its fields, options and events stay in the spec:

```json afora:entities
"Booking": {
	"fields": { "guest": "text", "status": { "enum": ["pending", "confirmed"] } },
	"change": ["status"],
	"events": { "onCreate": ["created"], "emits": ["confirmed"] },
	"implementation": { "import": "../handlers/booking#Booking" }
}
```

`generate` then writes `export class BookingBase extends entityOf(...) {}` in `src/domain/booking.entity.ts` (the file is named after the entity in kebab case), with `BookingEvents` bound to it. The class is written once, at the path the spec names (relative to the output directory), and extends the base:

Import the base from `booking.entity.ts`: `entities.ts` can import your class (an entity there with a `Booking` field), so importing the base through it would be a loop.

So that the base has no import cycle, every generated entity it needs through its fields, at any depth of blueprints and records, has a file of its own too, `<kebab-name>.entity.ts`, and leaves `entities.ts`; `index.ts` still exports it. What the generator cannot order is reported as `import_cycle`: a module that holds two classes where one names the other, an event handler or `upgrade` step in the module of the class, or a blueprint or record that names the entity while sharing its file with one the base needs. ## Standard use cases

A use case that a [standard use case](std-use-cases.md) covers is declared by naming it and the repository it is for, in place of its input, response and steps:

```json afora:partial
"useCases": {
	"CreatePost": {
		"generic": "create",
		"repository": "Posts",
		"description": "Writes a draft as the caller.",
		"options": {
			"as": "post",
			"omit": ["publishedAt"],
			"values": { "status": "draft" },
			"owner": { "key": "author", "context": "userId" },
			"errors": { "owner": "InvalidCredentials" }
		}
	},
	"ListPosts": { "generic": "list", "repository": "Posts" }
}
```

It generates `export const CreatePost = StdUseCases.context.create(Posts, { name: "CreatePost", ... })`, the same class a command would pick with `ctx.create(Posts, ...)`, and commands name it as any other use case. The options are those of the TypeScript form, with the exceptions of `errors` by name (declared, or exported by `@afora/core`); the name is the key of the declaration, and `description`, `tags` and `deprecated` go beside `generic`. `catalog().useCases` lists the standard use cases with the `actions` the repository needs, the `plugins` the entity needs and the `options` each takes.

`create` also takes `computed`, a list of keys of the entity the input does not take, which its `before` gives back (see [Computed keys](std-use-cases.md#computed-keys)).

The use cases that write (all but `get`, `list` and `login`) take the [hooks](std-use-cases.md#before-and-after) too: `before` and `after` are imports, as the `fn` of a `run` step, `dependencies` name declared use cases, repositories, environments or `"Logger"`, as those of a use case written in the spec, and `throws` lists exceptions as `errors` does (a name, or `{ "core": "Name" }`):

```json afora:useCases
"CreateEntry": {
	"generic": "create",
	"repository": "Entries",
	"options": {
		"before": { "import": "../hooks#checkEntry" },
		"after": { "import": "../hooks#recordEntry" },
		"dependencies": { "contentTypes": "ContentTypes", "logger": "Logger" },
		"throws": ["ContentTypeNotFound", "InvalidJsonData"]
	}
}
```

They generate `before: checkEntry, after: recordEntry, dependencies: { contentTypes: ContentTypes, logger: Logger }, throws: [ContentTypeNotFound, InvalidJsonData]`, with the functions imported from their module. Extraction needs `useCases.<Name>.before` and `useCases.<Name>.after` in `imports`. A field of any JSON value is `"json"` (`ctx.json`); a property made by `jsonOf({ schema })` is not written in the spec: extraction gives it as an opaque import.

The validator checks that the use case exists (`unknown_generic`), that the repository is declared (`unknown_repository`) and has the actions (`generic_requires_action`), that the entity has the plugins (`generic_requires_plugin`), and the shape of the options and the keys they name (`invalid_generic_option`; `invalid_import` for `before` or `after`, and the issues of a use case's `dependencies` for theirs). It also refuses what the use case would refuse when declared: `owner.key: "id"` on `create` or `register`, `owner` on `restore` without the action `exists`, a `computed` without a `before`, one that names a key twice, an unknown key, one that holds an entity or a list, or one also in `omit` or `values`, a `maxLimit` that is not a whole number above 0, a `where` of `list` that names a key twice or one that holds no scalar value, and `relations` on a key that holds no entity (`invalid_generic_option`), and an `update` with no change key an input can take, as for an entity whose only change key is sensitive (the `password` of `authenticatable`: use `changePassword`), or with `owner` on a change key that holds the owner (`generic_unavailable`). What else an option asks of the entity beyond its keys, such as omitting a required key, is checked by the use case itself when the generated code loads, which throws `UseCaseUnavailable`. `extractSpec` gives the declaration back as written, from `describe().useCases.<Name>.generic`, and needs no import mapped, a hashing function included, but for `before` and `after`.

## Routes and access

A use case in `afora.json` takes the same `route` and `access` as in TypeScript (see [Routes](use-cases.md#routes) and [Access](auth.md)), beside its description:

```json afora:partial
"useCases": {
	"ListPosts": {
		"route": {
			"method": "get",
			"path": "/posts/{slug}",
			"headers": { "locale": "accept-language" },
			"cookie": { "session": "sid" }
		},
		"access": { "scopes": ["posts:read"], "context": { "userId": "subject" } },
		"input": "ListPostsInput",
		"response": "PostList",
		"context": { "fields": { "userId": "id" } },
		"implementation": { "import": "../handlers/list-posts#ListPosts" }
	},
	"RemovePost": {
		"generic": "delete",
		"repository": "Posts",
		"route": { "method": "delete", "path": "/posts/{id}", "status": 204 },
		"access": { "scopes": ["posts:write"] }
	}
}
```

- **Generated as settings.** `route` and `access` become the settings of `useCaseOf`, and options of a standard use case; the generator writes no decorators, so the code runs on Node as it is.
- **Extracted from either form.** `extractSpec` reads what the class declares, whether it was written with the `route` setting or with `@Route` (and `access` or `@Access`). So a hand-written class may keep its decorators: its generated base carries the same declaration, and declaring the same route or access twice is accepted. A different one throws `InvalidUseCaseDeclaration` when the module loads.
- **A body on `delete`.** `"route": { "method": "delete", "path": "/subscriptions", "body": true }` reads the input keys with no other place from a JSON body instead of the query; `body` on another method is an `invalid_route` issue.
- **A status chosen at run time.** `"route": { "method": "get", "path": "/health", "statuses": [503] }` declares the other statuses the use case may answer with, each with the same response; an entry that is not a 2xx with a body (not `204` or `205`), a 4xx or a 5xx, that is `400` or `500` (kept for problems), a duplicate or the route `status` is an `invalid_route` issue. The status itself is chosen with `withStatus(503, body)`, in a hand-written `execute` or in the function of a `run` step whose result the `return` step gives (see [A status chosen at run time](use-cases.md#a-status-chosen-at-run-time)).
- **Checked against the spec.** For a use case written in the spec, each key a route places must be a key of the input (`setCookie`, of the response), no key may have two places, the `owner` of an access must name an input key and its `context` keys must be in the context: `invalid_route` and `invalid_access`. For a standard use case only the shape is checked, since its input follows the repository; the generated code checks the rest when it loads.
- **The route of a sink still wins.** The `route` option of a `hono` (or `fastify`, `express`, `elysia`, `openapi`) stage, by operation id, overrides the method, path, status, `statuses` and `body` (a `delete` that reads a JSON body), as in TypeScript.
- **Tokens.** `login` and `refresh` take `"token": { "secret": { "env": "JWT_SECRET" }, ... }` in `options`, and a sink `"auth": { "jwt": { "secret": { "env": "JWT_SECRET" } } }`; the secret is always the name of an environment variable (see [Tokens and sessions](auth.md#tokens-and-sessions)). `"versionFrom"` and `"rotate"` in `token` end sessions: `logout` (with `"owner": { "key": "id", "context": "userId" }`) and `changePassword` take `"token": { "versionFrom": "sessionVersion" }` to add 1 to that version (a required integer of the entity, in its `change` and `sensitive`), and the repository lists `increment`.
- **Hooks are code.** The middlewares and the authenticator of a sink are its second argument, which JSON cannot hold. A stage that needs them is written in a file and named with `{ "import": "./stages.ts#api" }`. `describe()` marks such a stage with `hooks: true`, so extraction throws an `ExtractionError` naming `outputs.<Name>.pipe.<index>` until it is mapped (`--import outputs.Api.pipe.0=./stages.ts#api`), and then writes `{ "import": "./stages.ts#api" }`: the generated code keeps the hooks instead of serving the output without them.

## Catalogs: providers, stages and event policies

A provider, a stage or an event policy that is not built in is not part of the spec. The spec names it (`"provider": { "use": "drizzle", "options": {...} }`, `{ "sink": "hono" }`, `"events": { "policy": "audit" }`) and a catalog, a codegen option, says which module and export make it.

```ts
export const providers = [
	{ name: "drizzle", module: "@afora/drizzle", export: "drizzleProvider" },
];
export const stages = [
	{ name: "hono", module: "@afora/hono", export: "hono", kind: "sink" },
];
export const policies = [
	{ name: "audit", module: "../policies.ts", export: "audit" }, // made by eventPolicyOf
];
```

- In the CLI, `--providers <module>`, `--stages <module>` and `--policies <module>` take a module that exports `providers` or `stages` (or has it as the default export), an array of those entries. The flags resolve the module as a file, not a package: `@afora/drizzle` and `@afora/hono` export their own entries, so a local module that re-exports them (`export { providers } from "@afora/drizzle";`, `export { stages } from "@afora/hono";`) passed as `--providers ./providers.ts --stages ./stages.ts` is enough.
- In code, they are the `providers`, `stages` and `policies` options of `validateSpec(spec, extended, options)` and `generate(spec, extended, options)`.
- `inMemory` is the only built-in provider, `select` and `openapi` the built-in stages (`StdStages` of `@afora/core`) and `publishEvents` the built-in event policy (`StdEventPolicies`); `catalog()` lists them.
- `module` is a package or a path relative to the output directory, and `export` is the factory, called with the options object (omitted when there are none). `kind` on a stage entry is optional and checks `transform` or `sink`.
- Provider options recurse over JSON values and `{ "import": "./x.ts#y" }` references, which become named imports. The validator never evaluates them.
- A bad entry is an `invalid_provider_catalog`, `invalid_stage_catalog` or `invalid_policy_catalog` issue; a name outside the catalog is `unknown_provider`, `unknown_stage` or `unknown_event_policy`. The options of an external policy are only checked to be JSON.

## Limitations

What the spec and the round trip do not cover. Each is reported by an issue or an `ExtractionError`, never silently dropped, unless it says otherwise.

- **An opaque provider needs a mapping.** A provider created without `providerOf` is opaque. `drizzleProvider({ db, tables })` is one: `db` and `tables` are not JSON, so it registers no descriptor and extraction needs `--import provider=./db.ts#provider` instead of guessing options. Without it, extraction throws instead of defaulting to memory.
- **Provider options come back as JSON.** A provider made with `providerOf({ name, options, create })` comes back as `"inMemory"` or `{ use, options }` with the JSON options it was given. A value that was an import reference when generating is not recovered.
- **Opaque properties.** A property declared with `propertyOf` that is not a Std one, or built on one that is not (custom handlers included), cannot be recreated, so it becomes `{ "opaque": true, "import": ... }`, imported from the key named after the property in `imports` or, when unmapped, from `./opaque` (a default that you must provide or map).
- **Function messages.** An exception whose message is a function comes back without `message`, so generation gives it the default `"<Name>."`.
- **Standard use cases come from `@afora/core`.** `generic` names a use case of `StdUseCases`; a use case plugin of another catalog cannot be named in a spec yet. A use case made by one in hand-written code is extracted as its steps.
- **Names are shared.** Every kind of declaration shares one namespace, so a command cannot be called `Users` while a repository already is.
- **Imported use cases and dependencies.** Any use case can list an imported one (a hand-written class, `{ "import": ... }`) as a dependency (see [When steps are not enough](#when-steps-are-not-enough)). What the generator cannot order is a hand-written module that holds several classes or functions which need each other through the generated files, such as two imported use cases in `../handlers/all.ts` where one depends on the other: the validator reports `import_cycle`, and the fix is a module per class. Two use cases whose files would have the same name (`GetURL` and `GetUrl` are both `get-url.use-case.ts`) are `file_collision`.
- **Hand-written use cases.** With `{ "import": "../handlers/register#Register" }`, the generated `register.use-case.ts` has `export abstract class RegisterBase extends useCaseOf({...}) {}`, also re-exported by `use-cases.ts`; your class extends it and implements `execute`, and `application.ts` registers your class. Import the base from `register.use-case.ts`: a handler that imports it from `use-cases.ts` works only as long as no other use case depends on that handler, since `use-cases.ts` then imports the handler. Extraction needs the `useCases.<Name>` mapping.
- **`Register` is written by hand.** The generated `application.ts` does not augment `Register` (two generated applications in one project would conflict), so `useApplication()` is `AnyApplication` until a file of yours declares it (see [Applications](applications.md#the-started-application)). A `provider` made with `providerFrom` is code, so it is an `{ "import": ... }`; `examples/blog` declares it as `"providers": { "database": { "import": "../provider.ts#database" } }` with `"provider": "database"` (`examples/blog/src/provider.ts`).
- **Named providers come from this spec or one it extends directly.** `"provider": "<key>"` names a key of the top-level `providers` of the spec or of a spec it `extends` directly (imported as `Providers` from its output). A key of a spec further up is reported as `unknown_provider`. A provider written as `"inMemory"` or `{ "use" }` is made when the module loads, so it is shared by every application that registers it; for one instance per application, import a `providerFrom` (`{ "import": "./audit.ts#audit" }`).
- **Step types are checked by TypeScript.** `check` follows the paths of `$input` and `$context` at any depth (`unknown_key` for `$input.address.zipp`), but knows nothing of the types of the results of steps or of the `run` functions. The generated steps use cases declare [`strictSteps: true`](use-cases.md#strict-steps), so type-checking the generated code reports a wrong path of a step result, an arg that does not fit the repository method, record method or `run` function, a `build` value the record does not take and a `return` the response does not take.
- **A `run` with `args` declares `params`.** `"params"` is a blueprint by name or `{ "fields": {...} }` whose fields match the `args` by position: the args are parsed before the function is called, and a wrong one throws `InvalidUseCaseStep` instead of reaching the function. `check` reports `run_without_params` for a `run` with `args` and no `params`, and `invalid_args` when the counts differ; a `run` without `args` needs no `params`. See [use cases](use-cases.md#steps).
- **Transactions are checked at run time.** `"transaction": true` needs a provider with transactions; the provider is unknown when the spec is validated, so `commandOf` throws `InvalidCommandDeclaration` when the code runs, not `validateSpec`.
- **Constructs the core does not describe.** A `change` on a plugin key and the order of `plugins` are not recovered.
- **Entity methods are written by hand.** An entity with methods names its class with `implementation` (see [Entities with methods](#entities-with-methods)); records take no `implementation`, so a record with methods is extended in a file of your own, and the generated code uses the generated class.
- **Generated code needs TypeScript 5.5 or newer** to type-check.
- **Extension by path.** `"extends": ["../auth/afora.json", "@acme/auth"]` takes the declarations of other specs; the same name for different declarations is a conflict, and the same declaration reached twice is registered once. The generated `application.ts` extends their `App`.
