# afora.json

An `afora.json` describes a domain as data: properties, blueprints, records, entities, environments, repositories, exceptions, use cases (with their steps), commands and outputs. `@afora/codegen` turns it into the TypeScript you would have written by hand, and turns an `Application` back into an `afora.json`. The code is committed and reviewable; nothing is interpreted at runtime.

This guide is the workflow. The reference of every declaration, option and issue code is in [packages/codegen](../packages/codegen/README.md), the same spec is authored by an agent through [packages/mcp](../packages/mcp/README.md), and `afora.schema.json` (in `@afora/codegen`) is its JSON Schema, for editors (`"$schema": "./node_modules/@afora/codegen/afora.schema.json"`).

## The workflow

```bash
bun add @afora/core typebox
bun add -d @afora/codegen
```

```bash
afora-codegen check [afora.json] [--providers module] [--stages module]                 # validate
afora-codegen generate [afora.json] [--out dir] [--providers module] [--stages module]  # write the code into output.dir
afora-codegen extract src/app.ts#App [--import key=./file.ts#name] > afora.json
```

1. Write the spec. The quick start in the [README](../README.md#the-same-app-as-an-aforajson) is a complete one.
2. `check` validates it. Every issue has a path, a stable `code` and a message, and `generate` throws `InvalidSpecError` with the same issues instead of writing a partial result.
3. `generate` writes one file per kind of declaration into `output.dir` (`src/domain` by default), an `application.ts` with `export const App = applicationOf({...})` and an `index.ts`. The output is deterministic, formatted as Biome would, and every file starts with `// Generated by @afora/codegen from afora.json. Do not edit.` It only overwrites or removes files that carry that banner, and writes nothing if one would be refused.
4. Add behavior in files of your own: extend a generated class, or point the spec at a hand-written function or class with `{ "import": "./file.ts#name" }`. Imports are relative to the output directory.
5. Commit the generated code. A test that generates again and compares it with the committed files catches drift; `examples/blog` does exactly that.

`extract` imports the file, so use Bun (or Node >= 23.6) for TypeScript files. The CLI runs on Node >= 22 or Bun. The same functions are available from code: `loadSpec`, `validateSpec`, `generate`, `writeGenerated`, `extractSpec`, `normalizeSpec`, `catalog`.

## Round trip

`extractSpec(app)` reads `app.describe()` and is the inverse of `generate`: `spec -> generate -> import -> extractSpec` gives back the same spec, and `normalizeSpec` makes the shorthand and object forms of a field compare equal. This holds for code that was generated, and for code written by hand, as long as everything the core cannot describe is mapped to an export (next section). An unmapped piece makes extraction throw an `ExtractionError` naming the key, instead of guessing. `examples/blog` extracts its own spec back in its tests, and `bun run test:roundtrip` proves both directions on complete applications.

## Mapping what cannot be described

Some things are code, not data: a provider made by hand, a `run` function, an `execute`, a command's event handler, a stage. Extraction needs to know where each one is exported from. In the CLI it is `--import key=./file.ts#name`, in code `extractSpec(app, { imports: { key: "./file.ts#name" } })`.

| Key                            | Maps                                                                    |
| ------------------------------ | ----------------------------------------------------------------------- |
| `provider`                     | the provider of the application, when created without `providerOf`      |
| `repositories.<Name>.provider` | the own provider of a repository, when created without `providerOf`     |
| `useCases.<Name>`              | a use case with a hand-written `execute`                                |
| `useCases.<Name>.run.<name>`   | the `fn` of a `run` step of a steps use case                            |
| `commands.<Name>.events`       | the event handler of a command                                          |
| `commands.<Name>.onEventError` | the `onEventError` handler of a command                                 |
| `outputs.<Name>.pipe.<index>`  | a stage written by hand, by its position in the `pipe`                  |
| `<property name>`              | the module of a property that cannot be recreated (see the limitations) |

The value is always `"./file.ts#export"`.

## Catalogs: providers and stages

A provider or a stage that is not built in is not part of the spec. The spec names it (`"provider": { "use": "drizzle", "options": {...} }`, `{ "sink": "hono" }`) and a catalog, a codegen option, says which module and export make it.

```ts
export const providers = [
	{ name: "drizzle", module: "@afora/drizzle", export: "drizzleProvider" },
];
export const stages = [
	{ name: "hono", module: "@afora/hono", export: "hono", kind: "sink" },
];
```

- In the CLI, `--providers <module>` and `--stages <module>` take a module that exports `providers` or `stages` (or has it as the default export), an array of those entries. `@afora/drizzle` and `@afora/hono` export their own entries, so `--providers @afora/drizzle --stages @afora/hono` is enough.
- In code, they are the `providers` and `stages` options of `validateSpec(spec, extended, options)` and `generate(spec, extended, options)`.
- `inMemory` is the only built-in provider, and `select` and `openapi` the built-in stages (`StdStages` of `@afora/core`); `catalog()` lists them.
- `module` is a package or a path relative to the output directory, and `export` is the factory, called with the options object (omitted when there are none). `kind` on a stage entry is optional and checks `transform` or `sink`.
- Provider options recurse over JSON values and `{ "import": "./x.ts#y" }` references, which become named imports. The validator never evaluates them.
- A bad entry is an `invalid_provider_catalog` or `invalid_stage_catalog` issue; a name outside the catalog is `unknown_provider` or `unknown_stage`.

## Limitations

What the spec and the round trip do not cover. Each is reported by an issue or an `ExtractionError`, never silently dropped, unless it says otherwise.

- **An opaque provider needs a mapping.** A provider created without `providerOf` is opaque. `drizzleProvider({ db, tables })` is one: `db` and `tables` are not JSON, so it registers no descriptor and extraction needs `--import provider=./db.ts#provider` instead of guessing options. Without it, extraction throws instead of defaulting to memory.
- **Provider options come back as JSON.** A provider made with `providerOf({ name, options, create })` comes back as `"inMemory"` or `{ use, options }` with the JSON options it was given. A value that was an import reference when generating is not recovered.
- **Opaque properties.** A property declared with `propertyOf` that is not a Std one, or built on one that is not (custom handlers included), cannot be recreated, so it becomes `{ "opaque": true, "import": ... }`, imported from the key named after the property in `imports` or, when unmapped, from `./opaque` (a default that you must provide or map).
- **Function messages.** An exception whose message is a function comes back without `message`, so generation gives it the default `"<Name>."`.
- **Names are shared.** Every kind of declaration shares one namespace, so a command cannot be called `Users` while a repository already is.
- **Imported use cases and dependencies.** A use case cannot list an imported use case (a hand-written class, `{ "import": ... }`) as a dependency: its handler imports the generated file that would import it back, which is an import cycle. The validator reports `import_dependency`.
- **Hand-written use cases.** With `{ "import": "../handlers/register#Register" }`, the generated file has `export abstract class RegisterBase extends useCaseOf({...}) {}`; your class extends it and implements `execute`, and `application.ts` registers your class. Extraction needs the `useCases.<Name>` mapping.
- **Transactions are checked at run time.** `"transaction": true` needs a provider with transactions; the provider is unknown when the spec is validated, so `commandOf` throws `InvalidCommandDeclaration` when the code runs, not `validateSpec`.
- **Constructs the core does not describe.** A `change` on a plugin key and the order of `plugins` are not recovered.
- **Repositories point at the generated classes.** To add behavior, extend the generated class in a file of your own.
- **Generated code needs TypeScript 5.5 or newer** to type-check.
- **Extension by path.** `"extends": ["../auth/afora.json", "@acme/auth"]` takes the declarations of other specs; the same name for different declarations is a conflict, and the same declaration reached twice is registered once. The generated `application.ts` extends their `App`.
