# Security policy

## Supported versions

All the `@afora/*` packages share one version and follow [VERSIONING.md](VERSIONING.md). Security fixes go to:

- the latest stable release (the `latest` dist-tag);
- the newest patch of each maintained `release/<YY>.<minor>` line (the `release-<YY>.<minor>` dist-tag), which receives only fixes;
- an open release candidate (the `rc` dist-tag), whose fix ships as the next candidate (`27.0.0-rc.2` after `27.0.0-rc.1`).

Older patches of a line, betas and the Next (`next`, published from `dev`) get no fixes of their own: upgrade to a version above.

## Reporting a vulnerability

Do not open a public issue. Report it privately through [GitHub's private vulnerability reporting](https://github.com/afora-framework/core/security/advisories/new), with:

- the affected package and version;
- what an attacker can do, and under which conditions;
- a minimal reproduction, if you have one.

You should get a first answer within a few days. Once a fix is published, the advisory is disclosed with credit to you, unless you ask otherwise.

## Scope

Of particular interest: sensitive values (a `sensitive` property such as `Password`) leaking through `toJSON()`, outputs or errors; password hashing and verification; validation that can be bypassed (undeclared keys, reserved keys, prototype pollution); and code generated by `@afora/codegen` or exposed by `@afora/mcp` and `@afora/hono`.

## Trust model of the tools that write code

`@afora/mcp` and `@afora/codegen` turn a spec into files and import modules of a project. Who supplies the spec decides what is trusted.

- **`@afora/mcp`** takes its input from an agent and treats it as untrusted. The server works on one project directory: every write is confined to it (resolved paths, no `..`, no symlink that leaves it, `afora.json` and `output.dir` included), a generated file is overwritten only if it carries the generator banner, and every module or spec file a spec names (`{ "import": ... }`, `extends`) must be a package or a file inside the project (`outside_project` otherwise); a package named by `extends` is looked up in the `node_modules` of the project only (never one of a parent directory, a package cache or the registry), and its spec, with what that spec extends, must really be inside `<project>/node_modules`. Absolute paths and URLs are refused, and so are the specifiers a runtime would resolve elsewhere than the path they spell: a backslash, a percent-encoded character, a `?` or a `#` (an import is resolved as a URL, where `\` is `/`, `%2e%2e` is `..` and `?` starts a query; each relative module is also resolved as a URL and must land inside), a package path with a `.` or `..` segment (`pkg/../../x` leaves `node_modules/pkg`) and a module built into the runtime (`fs`, `child_process`, `bun`). A relative path is refused when it, or any file a runtime may load for it (an added extension, the `.ts` of a `.js`, the `index` or `package.json` entry of a directory, the `afora.json` of an extended directory), goes through a symlink leaving the project. `output.dir` cannot be in `node_modules` or `.git` (in any case or spelling a file system folds to them, in the spellings Windows reads as them: trailing dots or spaces, a stream suffix, a short name such as `NODE_M~1`, or through a link to one), it is relative on every platform (no `/`, `\`, UNC path or drive such as `D:`), and a spec extended by a path, at any depth, is held to the same rules from its own directory, its own `output.dir` included, before what it extends is read. It executes nothing an agent sends: it imports the application of the project in a subprocess (which runs the project's own code), a `.ts`, `.tsx`, `.mts`, `.js` or `.mjs` module outside `node_modules` and `.git`, and only the `--app` module when the server was started with one, reports a failed import by a code, never with the module's source or what it threw, returns the `tsc` diagnostics of what it generated with their literals and quoted types redacted, reports a spec file that is not valid JSON without quoting it, names in its messages the files of the project from its root and never by an absolute path, and runs the `tsc` of the TypeScript the project has installed (`<project>/node_modules/typescript`, run by the server's own runtime, with `--pretty false`), never one of a parent directory, the `PATH`, a package cache or the registry; without it, nothing is type-checked, and a `tsc` that fails without a diagnostic is reported by its exit code, never with what it printed.
- **`@afora/codegen`** is run by the developer, on a spec of their own repository: the CLI trusts the spec as it trusts the code beside it. It still confines what it writes to the directory of the spec. A tool that feeds it a spec from an untrusted source should call `projectBoundaryIssues` first, as `@afora/mcp` does.
- **Out of scope:** what the project's own code does when imported, the packages the project depends on, and an agent that was given other tools to write files in the project.

A path or a module that escapes the project through either package is a vulnerability: please report it as above.
