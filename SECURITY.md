# Security policy

## Supported versions

afora is in `0.x`: only the latest published version of `@afora/core` and of each `@afora/*` package receives security fixes.

## Reporting a vulnerability

Do not open a public issue. Report it privately through [GitHub's private vulnerability reporting](https://github.com/afora-framework/core/security/advisories/new), with:

- the affected package and version;
- what an attacker can do, and under which conditions;
- a minimal reproduction, if you have one.

You should get a first answer within a few days. Once a fix is published, the advisory is disclosed with credit to you, unless you ask otherwise.

## Scope

Of particular interest: sensitive values (a `sensitive` property such as `Password`) leaking through `toJSON()`, outputs or errors; password hashing and verification; validation that can be bypassed (undeclared keys, reserved keys, prototype pollution); and code generated by `@afora/codegen` or exposed by `@afora/mcp` and `@afora/hono`.

## Trust model of the tools that write code

`@afora/mcp` and `@afora/codegen` turn a spec into files and import modules of a project. Who supplies the spec decides what is trusted.

- **`@afora/mcp`** takes its input from an agent and treats it as untrusted. The server works on one project directory: every write is confined to it (resolved paths, no `..`, no symlink that leaves it, `afora.json` and `output.dir` included), a generated file is overwritten only if it carries the generator banner, and every module or spec file a spec names (`{ "import": ... }`, `extends`) must be a package or a file inside the project (`outside_project` otherwise; absolute paths and URLs are refused). It executes nothing an agent sends: it imports the application of the project in a subprocess (which runs the project's own code) and runs `tsc`.
- **`@afora/codegen`** is run by the developer, on a spec of their own repository: the CLI trusts the spec as it trusts the code beside it. It still confines what it writes to the directory of the spec. A tool that feeds it a spec from an untrusted source should call `projectBoundaryIssues` first, as `@afora/mcp` does.
- **Out of scope:** what the project's own code does when imported, the packages the project depends on, and an agent that was given other tools to write files in the project.

A path or a module that escapes the project through either package is a vulnerability: please report it as above.
