# @afora/codegen

Describe a domain in an `afora.json` and generate the idiomatic [`@afora/core`](../../README.md) TypeScript for it: the code someone would write by hand (`blueprintOf`, `entityOf`, `recordOf`, `repositoryOf`, `environmentOf`, `applicationOf`), committed, readable and reviewable. It is codegen, not interpretation at runtime. The inverse works too: `extractSpec(app)` gives the `afora.json` of an `Application`.

```bash
bun add @afora/core typebox
bun add -d @afora/codegen
```

`@afora/core` and TypeBox (`typebox: ^1`) are peer dependencies. Generated files use the application's dependencies; codegen does not generate a package manifest.

```bash
afora-codegen check [afora.json]                 # validate
afora-codegen generate [afora.json] [--out dir]  # write the code into output.dir
afora-codegen extract src/app.ts#App > afora.json
```

`extract` imports the file, so use Bun (or Node >= 23.6) for TypeScript files. The CLI runs on Node >= 22 or Bun.

## The spec

`blueprint` and `options` are valid field names in records and entities. Their instance metadata lives under the core's `Meta` symbol; the JSON spec and class statics keep their existing shape.

```jsonc
{
	"$schema": "./node_modules/@afora/codegen/afora.schema.json",
	"version": 1,
	"name": "blog",
	"output": { "dir": "src/domain" },
	"properties": {
		"Age": {
			"base": "integer",
			"with": { "min": 0, "max": 150, "description": "In years" }
		},
		"Status": { "enum": ["draft", "published"] }
	},
	"blueprints": {
		"Address": {
			"fields": {
				"street": "string",
				"zip": { "type": "string", "with": { "pattern": "^\\d{5}-\\d{3}$" } }
			}
		}
	},
	"entities": {
		"User": {
			"fields": {
				"name": "text",
				"email": "email",
				"slug": "slug",
				"password": "password",
				"age": "Age?",
				"address": "Address",
				"tags": "string[]"
			},
			"unique": ["email"],
			"change": ["name"]
		},
		"Post": {
			"fields": {
				"title": "text",
				"status": "Status",
				"author": "User",
				"coauthors": "User[]"
			}
		}
	},
	"environments": {
		"Database": { "fields": { "DATABASE_URL": "url", "PORT": "integer" } }
	},
	"repositories": {
		"Users": {
			"entity": "User",
			"actions": ["findById", "findByEmail", "create", "update"],
			"environments": ["Database"]
		},
		"Posts": {
			"entity": "Post",
			"actions": ["findById", "findManyByAuthor", "create"],
			"relations": ["Users"]
		}
	}
}
```

Generated (`src/domain/entities.ts`):

```ts
// Generated by @afora/codegen from afora.json. Do not edit.

import { blueprintOf, entityOf, optionalOf } from "@afora/core";
import { Address } from "./blueprints";
import { Age } from "./properties";

export class User extends entityOf(
	blueprintOf((ctx) => ({
		name: ctx.text,
		email: ctx.email,
		// ...
		age: optionalOf(Age),
		address: Address,
		tags: ctx.list.string,
	})),
	{
		unique: ["email"],
		change: ["name"],
	},
) {}
```

**Fields.** A string is a shorthand: `"email"`, `"Age?"` (optional), `"string[]"` (list), `"User[]?"` (optional list). The object form is `{ "type", "optional", "list": true | { "minItems", "maxItems" }, "with": {...} }`, `{ "enum": [...] }` or `{ "fields": {...} }` (a nested object). Lowercase names are Std properties (`email`, `text`, `integer`, ...), PascalCase names are declarations of the spec. `with` is `Property.with` / `ctx.<property>(options)` and only takes the options valid for the type (`pattern` is not valid for an `integer`).

**Declarations.** `properties` are `{ base, with?, optional? }`, `{ enum, name?, default? }` or `{ opaque: true, ref?, import }` (a hand-written property, imported relative to the output directory instead of recreated). `blueprints` and `environments` have `fields`. `records` and `entities` have `fields`, `sensitive`, `unique`, `change` and `plugins` (`authenticatable`, `taggable`, ...). `repositories` have `entity`, `actions`, `relations` and `environments`. `useCases` is reserved and rejected in v1.

**Extending.** `"extends": ["../auth/afora.json", "@acme/auth"]` uses the declarations of other specs (a relative path to their `afora.json`, or a package that exports `./afora.json` and the generated code). The same name for different declarations is a conflict; the same declaration reached twice is registered once. The generated `application.ts` extends their `App`.

**Output.** One file per kind in `output.dir` (`properties.ts`, `blueprints.ts`, `records.ts`, `entities.ts`, `environments.ts`, `repositories.ts`), `application.ts` with `export const App = applicationOf({...})` and `index.ts`, each starting with `// Generated by @afora/codegen from afora.json. Do not edit.`. Kinds that need each other share one file (no import cycles), and the code is formatted as Biome would. To add behavior, extend the generated class in a file of your own. Limitation: repositories point at the generated classes.

## API

```ts
import {
	catalog,
	generate,
	validateSpec,
	extractSpec,
	normalizeSpec,
	loadSpec,
	writeGenerated,
	specSchema,
} from "@afora/codegen";

const { spec, extended } = await loadSpec("afora.json"); // also reads what it extends
const issues = validateSpec(spec, extended); // [{ path, code, message }], never throws
const files = generate(spec, extended); // [{ path, contents }], deterministic
await writeGenerated(projectDir, files); // confined to the project, banner-checked
const again = extractSpec(App, { extends: { auth: "../auth/afora.json" } });
```

- `validateSpec(spec, extended?)` reports unknown references, name collisions, cycles, reserved and identity keys, `unique`/`sensitive`/`change` naming missing keys, repository action rules (`findBy<Key>` only for unique keys: `id`, `unique`, `slug` fields and unique plugin keys; `findManyBy<Key>` only for the others), `relations` that do not cover exactly the entities held at any depth, and `with` options invalid for the type. Each issue has a stable `code`.
- `generate(spec, extended?)` throws `InvalidSpecError` (with `issues`) for an invalid spec.
- `catalog()` is read from `@afora/core` at runtime (`Std.properties`, `Std.factories`, `StdRecordPlugins`, the reserved keys): nothing is a list kept by hand.
- `extractSpec(app, { extends, outputDir, imports })` is the inverse of `generate`: `spec -> generate -> import -> extractSpec` gives back the same spec (`normalizeSpec` makes shorthand and object forms compare equal). Properties with custom handlers become opaque imports. Constructs the core does not describe (a `change` on a plugin key, the order of `plugins`) are not recovered.
- `writeGenerated(root, files)` writes only inside `root` (no `..`, no symlink out), overwrites and removes only files that carry the banner, and writes nothing if one is refused.
- `afora.schema.json` is the JSON Schema of the spec, for editors.

Generated code type-checks with TypeScript 5.5 or newer.
